## Шаг 1. Каталоги событий и метрик, конфигурация эксперимента (M)

Зачем: события, метрики и guardrails ссылаются друг на друга, поэтому сначала их описание.

### Модели

`EventType`:
- `id`, `key` (уникальный, например `purchase`), `name`, `description`.
- `requires_exposure bool` — привязывать ли событие к показу (для конверсий и ошибок `true`).
- `is_exposure bool` — само ли событие является показом варианта (ровно один такой тип должен существовать).
- `archived_at` — архивация вместо удаления (по ТЗ: создать / изменить / архивировать).

`Metric`:
- `id`, `key` (уникальный), `name`.
- `kind`: `count`, `conversion`, `error_rate`, `latency_percentile`.
- `event_type_id` — событие-источник; для конверсии и доли ошибок ещё `denominator_event_type_id` (обычно exposure).
- `percentile` (только для `latency_percentile`: 50, 95, 99), `value_field` (поле значения в событии, например `latency_ms`).

Конфигурация в эксперименте (попадает в snapshot версии, меняется только в `draft`):
- `experiment_metrics`: `experiment_id`, `metric_id`, `role` (`target` | `diagnostic`).
- `experiment_guardrails`: `experiment_id`, `metric_id`, `threshold`, `comparison` (`gt` | `lt`), `window_seconds`, `action` (`pause` | `revert_to_control`).

### Эндпоинты
- `POST/GET/PUT /api/v1/event-types`, `POST /api/v1/event-types/:id/archive` (admin, experimenter на запись).
- `POST/GET/PUT /api/v1/metrics`.
- В `POST/PUT /experiments` принимать `metrics[]` и `guardrails[]`.

### Правила и граничные случаи
- Нельзя ссылаться на архивированный тип события или несуществующую метрику.
- Нельзя менять тип события, на который уже ссылаются запущенные эксперименты (разрешить только имя и описание).
- При `submit` проверять: есть хотя бы одна target-метрика.
- Повторяющаяся метрика в одном эксперименте запрещена.

### Файлы (по образцу существующих)
`models/event_type.go`, `models/metric.go`, `domain/repository/*`, `repository/postgres/*`, `domain/service/*`, `http/dto/*`, `http/handlers/*`, миграция в `pkg/db/postgres/migration.go`.

## Шаг 2. Таргетинг DSL (M)

### Формат (JSON-дерево)
```json
{
  "and": [
    {"attr": "country", "op": "in", "value": ["RU", "KZ"]},
    {"attr": "version", "op": ">=", "value": "2.5.0"},
    {"not": {"attr": "platform", "op": "==", "value": "web"}}
  ]
}
```
- Узлы: `and[]`, `or[]`, `not{}`, лист `{attr, op, value}`.
- Операторы: `==`, `!=`, `in`, `>`, `>=`, `<`, `<=`.
- Атрибуты: минимум `country`, `version`, `platform` (набор лучше сделать конфигурируемым, а не `switch`).
- Пустое правило означает «подходят все».

### Что реализовать
- Парсер и валидация дерева (типы, неизвестный атрибут или оператор, глубина не больше 10, размер).
- `Evaluate(rule, attrs map[string]string) (bool, error)`.
- Сравнение версий: по числовым сегментам (`1.10` больше `1.9`), для `version` сегментное сравнение, для прочих числовых атрибутов числовое, для остальных строковое.
- Отсутствующий атрибут в запросе: правило с ним даёт `false` (кроме `!=` и `not`; зафиксировать это поведение в README).
- Колонка `targeting jsonb` в `experiments`, входит в snapshot версии, валидируется при create/update/submit.

### Файлы
`internal/domain/targeting/{ast.go,parse.go,eval.go,version.go}` — отдельный пакет без зависимостей от БД.

### Проверка
- [ ] Табличные тесты `Evaluate` (все операторы, вложенность, версии, отсутствующий атрибут).
- [ ] Тесты парсера на кривой JSON.

## Шаг 3. Decide API (L) — ядро платформы

### Контракт (уточнить по ТЗ)
`POST /api/v1/decide`
```json
{"subject_id": "user-42", "attributes": {"country": "RU", "version": "2.6.0", "platform": "ios"},
 "flag_keys": ["button_color", "new_checkout"]}
```
Ответ по каждому ключу: `value`, `decision_id`, `experiment_id`, `variant`, `source` (`default` | `experiment`).

### Алгоритм для одного флага
1. Флага нет → ошибка по контракту ТЗ (404 или пометка в ответе).
2. Нет эксперимента `running` для флага (paused даёт default) → `default`.
3. Таргетинг не подошёл → `default`.
4. Корзина: `bucket = uint64(sha256(experiment_salt + ":" + subject_id)[:8]) % 10000`. Соль — `experiment.id`, чтобы разные эксперименты расслаивали пользователей независимо.
5. `bucket >= audience_bp` → `default` (вне аудитории).
6. Иначе вариант выбирается по накопленным весам в **стабильном порядке** (сортировка вариантов по имени), так как сумма весов равна `audience_bp`.
7. Включён `revert_to_control` (шаг 6) → вернуть контрольный вариант для всех в аудитории.

### Свойства и как они достигаются
- **Детерминизм:** чистая функция от (конфигурация, subject, атрибуты), без `rand` и без времени.
- **Stickiness:** конфигурация после запуска заморожена, хеш не меняется, значит subject остаётся на варианте.
- **decision_id:** детерминированный UUIDv5 от `experiment_id + version + subject_id + flag_key`, чтобы одинаковый запрос давал одинаковый ответ и события однозначно привязывались.
- Запись решения в таблицу `decisions` (идемпотентно по `decision_id`: `INSERT ... ON CONFLICT DO NOTHING`) с атрибутами subject — они нужны отчётам для сегментации.

### Защита пользователя
- Конфигурация (в БД или переменные окружения): `max_concurrent_experiments_per_subject`, `cooldown_seconds`.
- Таблица `subject_exposures(subject_id, experiment_id, first_seen_at, last_seen_at)`.
- Если у subject уже `max` активных экспериментов, новые не назначаются (получает default); решение логируется с причиной `user_protection`.
- Cooldown: после завершения участия в эксперименте subject не попадает в другие в течение срока. Зафиксировать выбранное толкование в допущениях.

### Аутентификация продукта
Решить и записать: либо заголовок `X-Api-Key` (таблица ключей, роль `service`), либо переиспользовать `X-User-Id`. Для проверяющего проще ключ из `.env`/seed.

### Производительность
Кэш активных экспериментов в памяти с коротким TTL (5–10 с) или инвалидацией при смене статуса. Один запрос `decide` с N флагами не должен делать N запросов в БД.

### Файлы
`internal/domain/decision/{bucket.go,select.go}` (чистая логика), `domain/service/decide.go`, `repository/postgres/decisions.go`, `http/handlers/decide.go`.

### Проверка
- [ ] Один и тот же запрос 100 раз даёт идентичный ответ и `decision_id`.
- [ ] На 100 000 subject распределение близко к весам (допуск ±1%).
- [ ] Изменение `subject_id` меняет вариант только в пределах весов; смена порядка вариантов в запросе не влияет.
- [ ] Эксперимент `paused`/`draft` даёт default; вне аудитории даёт default; таргетинг отсекает.
- [ ] Защита пользователя: третий эксперимент при лимите 2 не назначается.

## Шаг 4. События и атрибуция (L)

### Эндпоинт
`POST /api/v1/events` (пакет, ограничить размер, например 1000):
```json
{"events": [{"event_id": "e-1", "type": "purchase", "decision_id": "…", "subject_id": "user-42",
             "timestamp": "2026-10-08T12:00:00Z", "properties": {"screen": "cart", "latency_ms": 120}}]}
```
Ответ: `{"accepted": 10, "duplicates": 2, "rejected": 1, "rejected_details": [{"event_id": "e-9", "reason": "..."}]}`.

### Правила приёма
- Неизвестный или архивный тип события → rejected (`unknown_type`).
- Нет обязательных полей / плохой формат времени → rejected (`invalid`).
- Событие старше 7 суток от момента получения → rejected (`too_old`); из будущего (больше допуска, например 5 минут) → rejected.
- Дубль `event_id` → duplicates (уникальный индекс, `ON CONFLICT DO NOTHING`, счёт по `RowsAffected`).
- Одна ошибка не должна ронять весь пакет.

### Атрибуция
- Таблица `events(event_id PK, type_id, decision_id, subject_id, event_ts, received_at, properties jsonb)`.
- Событие типа `requires_exposure` засчитывается, только если у того же `decision_id` есть событие exposure с `event_ts` не позже самого события.
- Привязку делаем **при построении отчёта** (join по `decision_id`, сравнение времени), а не при приёме. Так порядок прихода событий не важен, а опоздавший exposure «довязывает» уже пришедшие конверсии.
- Событие без exposure остаётся в таблице, но в отчёты не попадает; считать их для будущего показателя качества данных.

### Индексы
`(decision_id)`, `(type_id, event_ts)`, уникальный `(event_id)`. Рассмотреть партиционирование по времени (написать в разделе масштабирования README).

### Проверка
- [ ] Дубль не засчитывается дважды; повторная отправка того же пакета даёт `duplicates = N`.
- [ ] Конверсия, пришедшая раньше exposure, засчитывается после прихода exposure.
- [ ] Конверсия без exposure не попадает в отчёт.
- [ ] Событие старше 7 суток отклоняется, ровно 7 суток принимается (граница).

## Шаг 5. Отчёты и заключение (M–L)

### Эндпоинт
`GET /api/v1/experiments/:id/report?from=…&to=…&group_by=country|version|platform|screen`
- Окно `[from, to)`: начало включительно, конец исключительно.
- Если окно не задано — от запуска до сейчас/завершения.

### Что считаем (по каждому варианту)
- Размер выборки: число уникальных `decision_id` с exposure в окне.
- `count`: число засчитанных событий типа метрики.
- `conversion`: уникальные decision с целевым событием ÷ уникальные decision с exposure.
- `error_rate`: события-ошибки ÷ exposure (или по определению метрики).
- `latency_percentile`: перцентиль по полю `value_field` (в SQL `percentile_cont`).
- Сегментация: срез по атрибутам из `decisions` (country/version/platform) и по `properties.screen`.
- Метрики берутся из конфигурации эксперимента (target и diagnostic), не из кода.

### Заключение
`POST /experiments/:id/conclusion`: `{"outcome": "rollout_winner" | "rollback" | "no_effect", "winner_variant": "…", "justification": "…"}`.
- Только для `completed` (или переход в `completed` одновременно с заключением); одна запись на эксперимент, неизменяемая.
- `rollout_winner` требует `winner_variant`; обоснование обязательно.
- `GET /experiments/:id/conclusion`.

### Проверка
- [ ] Набор тестовых событий с заранее посчитанным ответом (положить в `testdata/`).
- [ ] Границы окна: событие ровно в `from` включено, ровно в `to` исключено.
- [ ] Пустое окно, эксперимент без событий — нули, а не ошибка/деление на ноль.

## Шаг 6. Guardrails (M)

### Воркер
- Фоновая горутина (запуск и остановка в `app.Run` по `ctx`), интервал из конфигурации (например 30 с).
- Для каждого `running` эксперимента с guardrails: посчитать метрику за `window_seconds` по тем же запросам, что в отчётах (общий код расчёта), сравнить с порогом.
- Срабатывание:
  - `pause`: `TransitionStatus(running → paused)`;
  - `revert_to_control`: флаг `forced_control` на эксперименте, Decide возвращает контроль для всех в аудитории.
- Запись в аудит `guardrail_triggers`: `experiment_id`, `metric_id`, `value`, `threshold`, `window_seconds`, `action`, `triggered_at`.
- Защита от повторов: условный переход статуса (как уже сделано), для `revert` — условие `WHERE forced_control = false`; при нескольких инстансах приложения — блокировка (`pg_try_advisory_lock`) или допущение «один инстанс» в README.
- Минимальный объём данных: не срабатывать при малой выборке (параметр `min_sample`), иначе ложные срабатывания.

### Эндпоинты
`GET /experiments/:id/guardrail-triggers`.

### Проверка
- [ ] Подать события, превышающие порог, дождаться тика — эксперимент `paused`, запись в аудите содержит значение, порог, окно, время, действие.
- [ ] Не превышающие — ничего не происходит.
