# 4. События и атрибуция

## Зачем

Decide говорит приложению, что показать. А события рассказывают платформе, **что произошло дальше**: пользователь увидел вариант, купил, получил ошибку. По событиям потом считаются отчёты и срабатывают guardrails.

Цепочка связей:
```
Decide ──► decision_id ──► события (exposure, purchase, ...) ──► отчёт по варианту
```
`decision_id` склеивает «что мы показали» с «что пользователь сделал».

## 1. Две новые таблицы (`models/event.go`)

- `Decision`: записанное решение (кто, какой эксперимент и версия, какой вариант, атрибуты). Пишется самим Decide.
- `Event`: принятое событие. Первичный ключ `event_id` (это же и защита от дублей).

```go
type Event struct {
    EventID     string        // PK, ключ дедупликации
    EventTypeID uuid.UUID     // ссылка на каталог
    DecisionID  *uuid.UUID    // может быть пустым (для событий без требования показа)
    SubjectID   string
    EventTS     time.Time     // КОГДА событие произошло (по клиенту)
    ReceivedAt  time.Time     // КОГДА мы его получили
    Properties  json.RawMessage
}
```
Важно различать `EventTS` и `ReceivedAt`: событие может прийти позже, чем случилось. Для атрибуции и отчётов важно время **события**.

Индекс `(decision_id, event_ts)` ускоряет главный запрос: «все события этого решения по порядку».

## 2. Приём пакета: `EventService.Ingest`

Запрос приходит пакетом до 1000 событий. Ответ всегда 200, если сам пакет корректен:
```json
{"accepted": 2, "duplicates": 1, "rejected": 1,
 "rejected_details": [{"event_id": "n1", "reason": "unknown_type"}]}
```
Разбор на уровне пакета (в DTO): пустой пакет или больше 1000 событий дают 400. А каждое событие разбирается **внутри сервиса отдельно**, поэтому `event_id` или `timestamp` с плохим форматом отклоняют только это событие, а не весь пакет. Для этого поля в DTO принимаются «как есть» (строки), а проверка и разбор делаются позже.

### Порядок работы
1. **Справочники одним запросом на пакет:** типы событий по ключам (`GetEventTypesByKeys`) и решения по идентификаторам (`GetDecisionsByIDs`). Не запрос на каждое событие, а два запроса на весь пакет.
2. **Проверка каждого события** (`validate`, чистая функция, без базы): либо готовое `models.Event`, либо причина отклонения.
3. **Вставка принятых** (`InsertEventsIdempotent`) и подсчёт принятых и дублей.

### Таблица причин отклонения

| Причина | Когда |
|---|---|
| `invalid_event` | нет `event_id` или он длиннее 128 символов; плохой формат времени (нужен RFC 3339); без решения и без `subject_id`; плохой формат `decision_id` |
| `unknown_type` | типа события с таким ключом нет в каталоге |
| `archived_type` | тип в архиве |
| `too_old` | событие старше 7 суток |
| `future_timestamp` | событие дальше 5 минут в будущем |
| `missing_decision` | тип требует показа (или сам является показом), а `decision_id` не указан |
| `unknown_decision` | такого решения нет (клиент не вызывал Decide) |
| `subject_mismatch` | указанный `subject_id` не совпадает с пользователем решения |
| `properties_too_large` | `properties` больше 8 КБ |

**Про 7 суток.** По ТЗ допустимо опоздание до 7 дней. Граница включительная: ровно 7 суток принимается, 7 суток и секунда отклоняется. Это покрыто тестом. **Про 5 минут в будущее:** часы клиента могут чуть расходиться с нашими, жёсткое «не из будущего» отклоняло бы нормальные события.

**Про `subject_id`.** Если у события есть решение, пользователь берётся **из решения**, а не из события. Источник истины один.

## 3. Дедупликация

Мобильное приложение при плохой сети отправляет одно и то же событие повторно. Нельзя считать его дважды.

Как работает:
```go
res := tx.Clauses(clause.OnConflict{DoNothing: true}).Create(&events[i])
inserted[i] = res.RowsAffected == 1
```
- `event_id` первичный ключ, поэтому вставка существующего конфликтует.
- `ON CONFLICT DO NOTHING` означает «при конфликте молча ничего не делать» (без ошибки).
- `RowsAffected == 1` значит вставилось (новое), `0` значит дубль.

Вставка идёт в **одной транзакции** по одному событию в цикле. Это проще, чем массовая вставка, потому что нужно знать про каждое событие отдельно, новое оно или дубль. Если пакет содержит один `event_id` дважды, второй вход в цикле тоже увидит конфликт и будет посчитан дублем.

**Правило:** выигрывает первое пришедшее событие. Если повтор содержит другие данные, он всё равно считается дублем и игнорируется. Это нужно записать в допущения.

Повторная отправка всего пакета безопасна и даёт `accepted = 0, duplicates = N` (проверено в живом сценарии).

## 4. Атрибуция: какие события засчитываются

Из ТЗ: конверсии и ошибки привязываются к решению, **только если был показ**. Иначе в конверсию попадали бы пользователи, которым вариант никто не показывал.

### Правило
1. Показ засчитывается всегда.
2. Событие типа без `requires_exposure` засчитывается всегда.
3. Событие типа с `requires_exposure` засчитывается, только если у этого `decision_id` есть показ с временем **не позже** самого события (`exposure_ts <= event_ts`).
4. Если показов несколько, берётся самый ранний.

### Примеры на оси времени

```
Случай А: засчитывается
  время →   показ ──────── покупка
                ✔             ✔  (показ раньше)

Случай Б: не засчитывается (before_exposure)
  время →   покупка ─────── показ
                ✘ (покупка до показа по времени)

Случай В: показа ещё нет (no_exposure)
  время →   покупка          (показ пока не пришёл)
                ✘ пока не засчитана

Случай Г: опоздавший показ
  пришли:   сначала покупка, потом (позже) показ с более ранним временем
  результат: после прихода показа покупка становится засчитанной

Случай Д: одно время
  показ и покупка в одну секунду → засчитана (знак <=)
```

### Почему атрибуция считается при чтении, а не при приёме
Если бы мы решали «засчитана или нет» в момент приёма, пришлось бы знать все будущие события. Но события приходят в любом порядке и с опозданием (мы специально это допускаем до 7 суток). Если решение принять при приёме, то покупка, пришедшая раньше показа, была бы навсегда отброшена, хотя по времени всё корректно.

Поэтому мы **храним всё** и вычисляем засчитанность при чтении по временам самих событий. Тогда порядок прихода не важен.

### Реализация
- `EventRepository.ListDecisionEvents`: SQL с JOIN событий и типов, по времени:
  ```sql
  SELECT e.*, t.key AS type_key, t.requires_exposure, t.is_exposure
  FROM events e JOIN event_types t ON t.id = e.event_type_id
  WHERE e.decision_id = ? ORDER BY e.event_ts, e.event_id
  ```
- `attribute(decision, rows)`: **чистая функция** (без базы), находит самый ранний показ и размечает события. Именно она покрыта тестами.
- Эндпоинт `GET /decisions/:id/attribution` показывает результат: для каждого события `attributed` и причину (`no_exposure` или `before_exposure`).

В отчётах (следующий шаг) то же правило придётся записать в SQL. Нужно, чтобы оба места давали одинаковый результат; поэтому правило описано одним абзацем выше.

## 5. Что связывает это с остальным
- Тип события из каталога (шаг 1) решает, **нужен ли показ**. Правило не прописано в коде.
- `decision_id` из Decide (шаг 3) делает возможной связь события с вариантом.
- Метрики (шаг 1) ссылаются на типы событий и будут считаться по этим данным (шаг 5).

## 6. Известные упрощения
- Решение, на которое ссылается событие, должно уже существовать (клиент обязан сначала вызвать Decide).
- Нет очереди и асинхронной обработки: приём синхронный. Для большого потока лучше принять в очередь и записывать пакетами.
- Нет проверки, что `properties` содержат поле, нужное метрике (например `latency_ms`); это проверяется при расчёте.
- Нет ограничения на частоту отправки (rate limit).

## 7. Как показать проверяющему
```
POST /events  {"events":[{"event_id":"e1","type":"exposure","decision_id":"<D>","timestamp":"…"},
                         {"event_id":"e2","type":"purchase","decision_id":"<D>","timestamp":"…"}]}
→ {"accepted":2,"duplicates":0,"rejected":0,...}
тот же запрос ещё раз  → {"accepted":0,"duplicates":2,...}
GET /decisions/<D>/attribution  → показ и покупка, обе attributed: true
```
Негативные: неизвестный тип, событие старше 7 суток, `decision_id` которого нет. Для неупорядоченных: сначала отправить покупку (`attributed: false`, `no_exposure`), потом показ (покупка стала `true`).
