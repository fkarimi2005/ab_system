# 0. Как устроен проект: общая основа

Прежде чем разбирать шаги, нужно понять каркас, на котором они стоят. Все остальные файлы этой папки опираются на него.

## 1. Слои и почему они такие

```
HTTP-запрос
   │
   ▼
handler   (internal/http/handlers)   принять запрос, проверить форму, вернуть ответ
   │  вызывает
   ▼
service   (internal/domain/service)  бизнес-правила: «можно ли», «что дальше»
   │  вызывает через интерфейс
   ▼
repository (internal/repository/postgres)  SQL: сохранить и прочитать
   │
   ▼
Postgres
```

| Слой | Знает про HTTP | Знает про SQL | Что делает |
|---|---|---|---|
| handler | да | нет | читает JSON, берёт `actor` из контекста, вызывает сервис, превращает ошибку в статус |
| service | нет | нет | все правила предметной области |
| repository | нет | да | один метод на один осмысленный запрос |

**Зачем так.** Правило «нельзя одобрить свой эксперимент» должно жить в одном месте. Если оно будет в хендлере, его нельзя проверить без HTTP. Если в SQL, его нельзя поменять без миграции. В сервисе его можно проверить обычным тестом.

Дополнительные папки:
- `models` — структуры, которые становятся таблицами (GORM) и одновременно JSON в snapshot.
- `dto` — структуры запросов и ответов. Они **отдельные от моделей**, чтобы наружу не утекали внутренние поля и чтобы формат API не ломался при изменении таблиц.
- `pkg/errs` — все «ожидаемые» ошибки как переменные (`ErrInvalidTransition` и т. д.).
- `internal/domain/targeting`, `internal/domain/decision` — **чистая логика без базы**. Их легко тестировать, и именно они сделаны детерминированными.

## 2. Путь одного запроса (пример: `POST /experiments/:id/approve`)

1. `router.go`: сначала `Recovery`, `TraceID`, `RequestLogger`, затем для группы `/api/v1` ещё `Authenticate`.
   - `TraceID` берёт заголовок `X-Trace-Id` или создаёт новый и кладёт в контекст. Он нужен, чтобы по одному идентификатору найти все строки лога запроса.
   - `Authenticate` читает `X-User-Id`, загружает пользователя из базы и кладёт `Actor{ID, Role}` в контекст. Нет пользователя: 401. Деактивирован: 403.
   - `/health` и `/ready` **вне** `/api/v1`, поэтому для них аутентификация не нужна.
2. `RequireRole(admin, approver)` пропускает только эти роли, иначе 403.
3. Хендлер `decide(...)` разбирает UUID из URL, достаёт `actor`, вызывает `ApprovalService.Approve`.
4. Сервис загружает эксперимент, проверяет статус и владельца, пишет решение, считает порог, меняет статус.
5. Репозиторий выполняет SQL.
6. Ошибка идёт обратно вверх. `writeError` вызывает `mapError`, который по типу ошибки выбирает HTTP-статус.

## 3. Ошибки: как это работает

В `pkg/errs` объявлены «ожидаемые» ошибки:
```go
var ErrInvalidTransition = errors.New("недопустимый переход статуса")
```
Сервис возвращает их, а хендлер превращает в статус через `mapError` (файл `handlers/common.go`):

| Группа ошибок | Статус |
|---|---|
| не найдено (`ErrExperimentNotFound`, `ErrMetricNotFound`, ...) | 404 |
| конфликт (`ErrInvalidTransition`, дубль, `ErrActiveExperimentExists`) | 409 |
| нет прав (`ErrPermissionDenied`, `ErrNotInApproverGroup`) | 403 |
| неверные данные (`ErrInvalidField`, `ErrInvalidMetric`, ...) | 400 |
| всё остальное | 500, текст скрыт: «внутренняя ошибка сервера» |

### Оборачивание с деталями
В сервисах каталогов и таргетинга ошибка нужна и как **категория** (для статуса), и как **деталь** (что именно не так). Для этого есть помощник:
```go
func invalid(base error, format string, args ...any) error {
    return fmt.Errorf("%w: %s", base, fmt.Sprintf(format, args...))
}
```
`%w` сохраняет оригинальную ошибку внутри, и `errors.Is(err, errs.ErrInvalidMetric)` продолжает работать. Поэтому `mapError` даст 400, а пользователь увидит «некорректная метрика: percentile должен быть одним из [50 90 95 99]».

**Запомните:** `errors.Is` ищет ошибку по цепочке обёрток. Сравнение через `==` с обёрнутой ошибкой не сработает.

## 4. Логирование ошибок

`writeError` делает `c.Error(err)`: прикладывает ошибку к запросу. `RequestLogger` после обработки читает `c.Errors.Last()` и пишет одну JSON-строку:
```json
{"level":"WARN","msg":"http request","method":"POST","path":"/api/v1/experiments/:id/approve",
 "status":403,"err":"недостаточно прав...","trace_id":"...","user_id":"..."}
```
Уровень зависит от статуса: 5xx это `ERROR`, 4xx это `WARN`, остальное `INFO`. Логи идут в консоль и в `.logs/app.log`. Если раньше «ошибок не было видно», то потому что логировались только 5xx, а доменные ошибки (403/409) не логировались совсем.

## 5. База данных

- Таблицы создаёт `AutoMigrate` (`pkg/db/postgres/migration.go`) при старте. Это просто, но AutoMigrate **не удаляет и не меняет** уже существующие колонки. Если поменяли тип поля в модели, на старой базе придётся пересоздать таблицу или удалить том Docker.
- Одно правило держится не в Go, а в самой базе: **не более одного `running`/`paused` эксперимента на флаг**. Это частичный уникальный индекс:
  ```sql
  CREATE UNIQUE INDEX uniq_active_experiment_per_flag
  ON experiments (feature_flag_id)
  WHERE status IN ('running', 'paused') AND deleted_at IS NULL
  ```
  Почему в базе, а не в сервисе: две параллельные попытки запуска могут обе пройти проверку в коде. База же гарантирует уникальность атомарно. Условие `AND deleted_at IS NULL` исключает из индекса мягко удалённые эксперименты, чтобы они не блокировали флаг.
- Смена статуса атомарна: `UPDATE experiments SET status=to WHERE id=? AND status=from`. Если статус уже изменили, затронуто 0 строк, и мы возвращаем `ErrInvalidTransition`. Так закрыта гонка двух одновременных запросов.

## 6. Как собирается приложение

`internal/app/app.go` создаёт репозитории, из них сервисы, из сервисов хендлеры, и передаёт хендлеры в роутер. Это называется «внедрение зависимостей вручную»: никакой магии, каждая зависимость видна в одном месте.

Сервисы часто принимают **узкие интерфейсы**, например:
```go
type flagByKeyFinder interface {
    GetFeatureFlagByKey(ctx context.Context, key string) (models.FeatureFlag, error)
}
```
Сервису не нужен весь репозиторий флагов, ему нужен один метод. Это даёт возможность подставить в тесте крошечную подделку вместо базы.

Ещё одна техника для тестов: время передаётся не вызовом `time.Now()` внутри логики, а полем `now func() time.Time`. В тесте его подменяют на фиксированное значение, и проверка «ровно 7 суток назад» становится точной.

## 7. Чистая логика против логики с базой

| Пакет | Зависит от базы | Тестируется |
|---|---|---|
| `targeting` | нет | таблицами значений |
| `decision` | нет | границы корзин, распределение |
| `service/*` | через интерфейсы | подделками репозиториев |
| `repository/postgres` | да | только на живой базе |

Правило, которое здесь работает: **всё сложное и важное выносим в чистые функции**. Они быстро проверяются, и им можно доверять.

## 8. Как проверяющий будет это смотреть (для B7)

Готовая фраза: «Слои handler → service → repository, зависимости через интерфейсы, ошибки как значения с единым отображением на HTTP-статусы, структурные логи с trace_id, правило уникальности активного эксперимента гарантируется индексом в БД, смена статуса атомарна условным UPDATE».
