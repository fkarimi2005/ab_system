# 2. Таргетинг: правило «кому показывать эксперимент»

## Идея

Эксперимент можно ограничить аудиторией: «только Россия и Казахстан, версия приложения от 2.5.0, не web». Правило хранится в эксперименте как JSON-дерево и вычисляется при каждом запросе Decide.

```json
{"and": [
  {"attr": "country",  "op": "in", "value": ["RU", "KZ"]},
  {"attr": "version",  "op": ">=", "value": "2.5.0"},
  {"not": {"attr": "platform", "op": "==", "value": "web"}}
]}
```

Читается: страна из списка **И** версия не меньше 2.5.0 **И НЕ** web.

Код целиком лежит в отдельном пакете `internal/domain/targeting` и **не зависит от базы**. Это сделано специально: пакет чистый, поэтому его проверяют обычными тестами.

## 1. Структура данных (`rule.go`)

```go
type Node struct {
    And []Node `json:"and,omitempty"`   // все вложенные должны быть истинны
    Or  []Node `json:"or,omitempty"`    // хотя бы одно
    Not *Node  `json:"not,omitempty"`   // отрицание одного вложенного

    Attr  string `json:"attr,omitempty"`   // лист: атрибут
    Op    string `json:"op,omitempty"`     //       оператор
    Value any    `json:"value,omitempty"`  //       значение (строка или массив строк)
}
```

Дерево состоит из узлов трёх «логических» видов (`and`, `or`, `not`) и **листьев** (условие `attr op value`). В одном узле должен быть заполнен ровно один вид, иначе `{"and": [...], "not": {...}}` было бы неоднозначным.

`Value` имеет тип `any`, потому что бывает строкой (`"RU"`) или массивом (`["RU","KZ"]`). После разбора JSON строки приходят как `string`, массивы как `[]any`.

## 2. Разбор и проверка: `Parse`

```go
func Parse(raw []byte) (*Node, error)
```
Шаги:
1. Пустой ввод, пробелы или `null` означают «правила нет», то есть подходят все. Возвращается `nil, nil`.
2. `json.NewDecoder(...).DisallowUnknownFields()` отвергает опечатки вроде `"adn"` вместо `"and"`. Без этого опечатка молча превращалась бы в пустое правило.
3. `validate(depth)` проверяет дерево рекурсивно.

### Что проверяет `validate`
- Глубина не больше 10 (`maxDepth`): защита от злонамеренно глубоких деревьев, которые могут «подвесить» разбор.
- **Ровно один вид** в узле: считаем, сколько из `And`, `Or`, `Not` и «признаков листа» заполнено; должно быть ровно 1.
- `and`/`or` не пустые.
- Лист (`validateLeaf`):
  - атрибут из разрешённого списка `Attributes` (`country`, `platform`, `version`);
  - оператор допустим для его вида: `==`, `!=`, `in` для всех; `>`, `>=`, `<`, `<=` **только для версии**;
  - значение: непустая строка (для `in` непустой массив строк); для версии ещё и корректный формат.

### Новый атрибут добавляется одной строкой
```go
var Attributes = map[string]Kind{
    "country":  KindString,
    "platform": KindString,
    "version":  KindVersion,
}
```
Это ответ на принцип «ничего не зашито»: код вычисления не меняется.

### Почему это важно: безопасные приведения типов
Позже в `Matches` стоит `n.Value.(string)` без проверки. Это безопасно **только потому**, что `Parse` уже всё проверил. Поэтому правило нельзя собирать руками в обход `Parse`.

## 3. Вычисление: `Matches`

```go
func (n *Node) Matches(attrs map[string]string) bool
```
Рекурсия:
- `nil` правило подходит всем;
- `and`: все вложенные истинны (останавливаемся на первом ложном);
- `or`: хотя бы одно истинно;
- `not`: `!вложенное`;
- лист: `matchLeaf`.

### Лист (`matchLeaf`)
1. Если атрибута нет в запросе, лист **ложен**.
2. `in`: совпадает ли значение с любым из списка.
3. `==` / `!=`: сравнение (для версии по числам, для остальных строк).
4. `>`, `>=`, `<`, `<=`: сравнение версий.

### Таблица: отсутствующий атрибут
Решение, принятое сознательно и описанное в «допущениях»:

| Правило | Атрибута нет в запросе | Результат |
|---|---|---|
| `country == "RU"` | нет `country` | ложь |
| `country != "RU"` | нет `country` | **ложь** (не «истина»!) |
| `not(country == "RU")` | нет `country` | истина |

Логика такая: «неизвестно, какая у пользователя страна», значит ни одно условие про страну не подтверждено. А `not` инвертирует результат ложного листа, поэтому `not(country == "RU")` истинно. Это поведение нужно знать и уметь объяснить.

## 4. Сравнение версий (`version.go`)

Почему нельзя сравнивать строки: `"2.10" < "2.9"` как строки, потому что `'1' < '9'`. А версия 2.10 новее.

Алгоритм:
1. `parseVersion("2.10.1")` даёт `[2, 10, 1]` (каждый сегмент в число; отрицательное или нечисловое: ошибка).
2. `compareVersions(a, b)` идёт по сегментам слева направо. Недостающие сегменты считаются нулями, поэтому `2.5` равно `2.5.0`. Первый отличающийся сегмент решает.

Пример: `2.10` против `2.9`: сегменты `[2,10]` и `[2,9]`, первый равен, второй `10 > 9`, значит `2.10` новее.

Если в **запросе** пришла мусорная версия (`"abc"`), любое сравнение с ней ложно, а не паника.

## 5. Как это подключено к эксперименту

1. **Модель:** `Targeting json.RawMessage` с тегом `gorm:"type:jsonb"`. Тип `json.RawMessage` выбран, чтобы в snapshot версии правило сериализовалось как **вложенный JSON**, а не строка с экранированием. Отдельная зависимость (`datatypes`) не нужна.
2. **Сохранение** (`service/experiment_targeting.go`, `normalizeTargeting`): вызывает `Parse`; пустое правило превращается в `nil` (в базе `NULL`), корректное сохраняется как пришло. Ошибка разбора оборачивается в `ErrInvalidTargeting` с подробностью.
3. **Когда проверяется:** при создании, обновлении и при `submit` (`validateForReview`).
4. **Запрос `PUT`:** в `UpdateExperiment` пришлось добавить `"Targeting"` в `Select("Name", "AudienceBP", "Targeting", "Version")`. Без этого GORM не записывает поле. Это самая типичная ошибка при подключении нового поля.
5. **Версии:** правило входит в snapshot, поэтому изменение таргетинга порождает новую версию.
6. **`PUT` заменяет всё:** если в теле нет `targeting`, правило снимается (становится «подходят все»). Это тоже нужно записать в допущения.

## 6. Использование в Decide и защита от битых данных

```go
func matchesTargeting(ctx, exp, attrs) bool {
    rule, err := targeting.Parse(exp.Targeting)
    if err != nil { warn(...); return false }   // «fail closed»
    return rule.Matches(attrs)
}
```
Сохранённое правило уже проверено, поэтому ошибка здесь «невозможна». Но если случится (кто-то правил базу руками), мы **закрываем** эксперимент (все получают значение по умолчанию) и пишем предупреждение. Принцип: при сомнении безопаснее не показывать эксперимент, чем показать не тем.

Правило разбирается при каждом запросе Decide. Это упрощение: при большой нагрузке результат разбора можно кэшировать по `(experiment_id, version)`.

## 7. Как показать проверяющему
```
POST /experiments  {..., "targeting": {"attr":"country","op":"in","value":["RU","KZ"]}}
POST /decide  {"subject_id":"u1","attributes":{"country":"RU"},...}  → source: experiment
POST /decide  {"subject_id":"u1","attributes":{"country":"US"},...}  → source: default
POST /experiments  {..., "targeting": {"attr":"age","op":"==","value":"1"}}  → 400, понятная причина
```
