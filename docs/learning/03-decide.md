# 3. Decide API: какое значение флага показать пользователю

Это главная точка платформы. Все остальные шаги либо готовят данные для неё (флаги, эксперименты, таргетинг), либо обрабатывают её результаты (события, отчёты).

## 1. Запрос и ответ

```
POST /api/v1/decide
{"subject_id": "user-42",
 "attributes": {"country": "RU", "version": "2.6.0", "platform": "ios"},
 "flag_keys": ["button_color", "new_checkout"]}
```
```json
{"decisions": [
  {"flag_key": "button_color", "value": "red", "value_type": "string", "source": "experiment",
   "decision_id": "490e68b6-...", "experiment_id": "...", "variant": "red"},
  {"flag_key": "new_checkout", "value": "false", "value_type": "bool", "source": "default"}
]}
```

- `subject_id` стабильный идентификатор пользователя или устройства.
- `source` говорит, откуда значение: `experiment`, `default` или `unknown_flag` (такого флага нет; `value` тогда `null`).
- `decision_id` есть **только** у решений из эксперимента. Для значения по умолчанию связывать с событиями нечего.
- Ответ по каждому ключу идёт **в порядке запроса**, чтобы клиенту было просто разбирать.
- Если флага нет, это не ошибка всего запроса: отвечаем по остальным флагам, а для этого ставим `unknown_flag`. Один опечатанный ключ не должен ломать экран.

## 2. Алгоритм для одного флага (`decideOne`)

```
флаг по ключу найден?                         нет → unknown_flag
есть running-эксперимент на этот флаг?         нет → default
пользователь подходит под таргетинг?            нет → default
корзина пользователя попадает в аудиторию?      нет → default
иначе: вариант по весам → значение варианта + decision_id
```
Берётся только статус `running`. Эксперимент на паузе (`paused`) даёт значение по умолчанию: пауза и есть способ «временно выключить» эксперимент.

## 3. Корзина: `Bucket` (`internal/domain/decision/decision.go`)

Нужно, чтобы **один и тот же пользователь всегда попадал в один и тот же вариант**, но разные пользователи делились поровну. Для этого вместо случайного числа используется хеш:

```go
func Bucket(experimentID uuid.UUID, subjectID string) int {
    sum := sha256.Sum256([]byte(experimentID.String() + ":" + subjectID))
    return int(binary.BigEndian.Uint64(sum[:8]) % models.FullAudienceBP)   // 0..9999
}
```
Пошагово:
1. Склеиваем идентификатор эксперимента и идентификатор пользователя в строку.
2. SHA-256 даёт 32 «случайных» (но воспроизводимых) байта.
3. Берём первые 8 байт как число.
4. Остаток от деления на 10 000 даёт корзину от 0 до 9999.

**Почему 10 000, а не 100.** Доли аудитории и веса хранятся в «базисных пунктах»: 100% равно 10 000, 1% равно 100, 0,01% равно 1. Это позволяет задавать доли точнее процента и обходиться целыми числами (никаких ошибок округления дробей).

**Зачем в хеше идентификатор эксперимента.** Если брать только `subject_id`, пользователь, попавший в первые 20% одного эксперимента, попадал бы в первые 20% всех экспериментов. Эксперименты бы «коррелировали» и портили друг другу результаты. С идентификатором эксперимента в хеше разные эксперименты делят пользователей независимо.

**Про равномерность.** Остаток от деления даёт ничтожный перекос (~10⁻¹⁵), которым можно пренебречь.

## 4. Выбор варианта: `Select`

```go
func Select(variants []models.ExperimentVariant, audienceBP, bucket int) (models.ExperimentVariant, bool)
```
Корзины от 0 до `audienceBP - 1` делятся между вариантами **подряд, по весам, в порядке имён**.

Пример: аудитория 20% (`audience_bp = 2000`), варианты `blue` (вес 1000) и `red` (вес 1000):

```
корзина:   0 ......... 999 | 1000 ......... 1999 | 2000 ........ 9999
           └── blue ──────┘  └──── red ───────┘    └ вне аудитории ┘
                                                     (default)
```
- `bucket = 999` → blue; `1000` → red; `1999` → red; `2000` → вне аудитории.

Код идёт по отсортированным вариантам с накопленной суммой весов и берёт первый, у которого `bucket < накопленная сумма`.

**Почему сортировка по имени.** Порядок вариантов в базе не гарантирован. Без сортировки при другом порядке чтения пользователи «переехали» бы в другой вариант. Сортировка делает результат независимым от этого.

**Почему всё сходится.** Сумма весов равна `audience_bp` (проверяется при сохранении эксперимента в `ValidateConfig`), поэтому каждая корзина внутри аудитории попадает ровно в один вариант. Если вдруг веса не покрывают аудиторию (испорченные данные), `Select` честно отвечает «вне аудитории».

## 5. decision_id: `ID`

```go
func ID(experimentID uuid.UUID, version int, subjectID, flagKey string) uuid.UUID {
    name := experimentID.String() + ":" + strconv.Itoa(version) + ":" + subjectID + ":" + flagKey
    return uuid.NewSHA1(uuid.NameSpaceOID, []byte(name))     // UUID версии 5
}
```
UUIDv5 это детерминированный идентификатор: одинаковые входы дают одинаковый UUID. Следствия:
- повторный запрос того же пользователя вернёт **тот же** `decision_id` (требование «одинаковые запросы дают одинаковые результаты»);
- при записи в базу решения не размножаются (`ON CONFLICT DO NOTHING`);
- в идентификатор входит версия эксперимента: после изменения конфигурации идентификаторы будут новыми.

## 6. Три свойства из ТЗ и как они достигнуты

| Свойство | Как достигнуто |
|---|---|
| **Детерминизм**: одинаковый запрос, одинаковый ответ | нет ни `rand`, ни текущего времени в выборе; только хеш и данные эксперимента |
| **Stickiness**: пользователь не «прыгает» между вариантами | хеш не меняется, и конфигурация после запуска заморожена (редактировать можно только `draft`) |
| **Защита пользователя** (лимит экспериментов, cooldown) | **не реализовано**; это известный пробел |

Заморозка конфигурации тоже часть stickiness: если бы после запуска можно было менять веса, границы корзин сдвинулись бы, и часть пользователей перескочила бы в другой вариант.

## 7. Запись решений

После вычисления всех флагов сервис сохраняет решения из экспериментов **одним пакетом** (`RecordDecisions`, `ON CONFLICT DO NOTHING`):
```
Decision{DecisionID, ExperimentID, ExperimentVersion, FlagKey, SubjectID, Variant, Attributes, DecidedAt}
```
Зачем: события потом ссылаются на `decision_id`, и платформе нужно знать, что это за решение, какому пользователю оно принадлежит и какие у него были атрибуты (для сегментации в отчётах).

Если запись не удалась, Decide возвращает 500. Иначе клиент получил бы `decision_id`, под которым события потом будут отклонены как «неизвестное решение». Лучше отказать сразу.

## 8. Производительность и известные упрощения

- На каждый флаг идёт два запроса (флаг, эксперимент). Для запроса из 100 флагов это 200 запросов. Улучшение: кэш запущенных экспериментов с коротким TTL или загрузка пачкой.
- Запись решений синхронная.
- Права: Decide доступен любому авторизованному (включая viewer). В реальной системе продукт ходил бы по ключу API. Это допущение для README.
- Защита пользователя не сделана.

## 9. Как устроены тесты

- `decision_test.go`: границы корзин (`999` blue, `1000` red, `2000` вне), независимость от порядка вариантов, 100 000 пользователей дают доли 10% / 10% / 80% с допуском ±1%, `ID` зависит от каждого входа.
- `service/decision_test.go`: подставные репозитории; детерминизм (50 повторов), доля аудитории, таргетинг, битое правило, запись решений.

## 10. Как показать проверяющему
1. Создать флаг `button_color` (default `green`), эксперимент 100% с вариантами blue и red, довести до `running`.
2. `decide` для `user-1` пять раз: ответ идентичный, `decision_id` один и тот же.
3. `decide` для 1000 разных пользователей: примерно половина red.
4. `pause`: все получают `green`. `resume`: тот же пользователь получает тот же вариант, что раньше (stickiness).
