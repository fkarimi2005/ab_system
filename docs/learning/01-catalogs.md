# 1. Каталоги событий и метрик, метрики и guardrails в эксперименте

## Зачем это вообще нужно

В ТЗ главный принцип: **ничего не зашито в код**. Нельзя написать `if event == "purchase"` в Go. Типы событий, метрики и предохранители должны задаваться данными. Тогда продукт может завести новое событие `add_to_cart` без новой версии платформы.

Поэтому есть два справочника (каталога) и привязка их к эксперименту:

```
EventType  ──┐
(что за событие)   ├──► Metric ──► ExperimentMetric  (какие метрики считаем, target/diagnostic)
                   │              └► ExperimentGuardrail (при каком значении что делать)
```

## 1. Каталог типов событий (`models/event_type.go`)

```go
type EventType struct {
    Key              string   // уникальный, неизменный: "purchase"
    Name, Description string
    RequiresExposure bool     // засчитывать только после показа
    IsExposure       bool     // это сам показ варианта
    ArchivedAt       *time.Time
}
```

### Что значат два флага
- `IsExposure`: событие «пользователь увидел вариант». Без него нельзя честно считать конверсию: если считать всех, кто нажал, получим «конверсию» от нуля показов.
- `RequiresExposure`: «это событие имеет смысл только у тех, кто видел вариант». Покупка и ошибка API требуют показа. Просмотр страницы не требует.

Это и есть «политика атрибуции по типу события» из ТЗ. Она **данные**, а не код.

### Правила (`service/catalog.go`, `EventTypeService`)
| Правило | Почему |
|---|---|
| `key` по шаблону `^[a-z][a-z0-9_]{1,63}$` | ключ участвует в запросах, нужен предсказуемый безопасный формат |
| ключ уникален и после создания не меняется | на ключ ссылаются клиенты в потоке событий |
| активный тип показа только один | иначе непонятно, какое событие считать показом |
| тип показа не может требовать показа | логическое противоречие (показ нужен для самого показа) |
| тип показа нельзя архивировать | на нём держится вся атрибуция |
| архивация вместо удаления | старые события ссылаются на тип, удалять нельзя |

### Как проверяется «один тип показа»
```go
if in.IsExposure {
    exists, _ := s.repo.ActiveExposureTypeExists(ctx)
    if exists { return nil, errs.ErrExposureTypeExists }  // 409
}
```
Это проверка в сервисе. Не идеальная (две параллельные регистрации обе пройдут), но тип показа создают раз в жизни системы, поэтому для проекта это осознанное упрощение. Его нужно записать в «допущения». Идеальный вариант: частичный уникальный индекс `WHERE is_exposure AND archived_at IS NULL`.

## 2. Каталог метрик (`models/metric.go`)

Четыре вида (`MetricKind`):

| Вид | Что считает | Нужные поля |
|---|---|---|
| `count` | число событий | `event_type_id` |
| `conversion` | доля показов, где было целевое событие | `event_type_id`, знаменатель опционально |
| `error_rate` | доля показов, где была ошибка | то же |
| `latency_percentile` | перцентиль числового поля события | `percentile` (50/90/95/99), `value_field` |

### Проверка формы метрики: `validateMetricShape`
Это чистая функция, она не ходит в базу. Правила:
- `count`: нельзя задавать знаменатель, перцентиль и поле значения;
- `conversion`/`error_rate`: нельзя перцентиль и поле значения;
- `latency_percentile`: нужны перцентиль из допустимого списка и `value_field` по шаблону, знаменатель нельзя.

**Зачем настолько строго.** Если разрешить «лишние» поля, у метрики появится неоднозначность: что значит `count` с перцентилем? Лучше отказать сразу, чем гадать при расчёте отчёта.

Потом в `Create` идёт проверка с базой: тип события есть и не в архиве (`activeEventType`).

### Метрику нельзя менять, можно только переименовать
```go
func (s *MetricService) Rename(...)  // меняет только name
```
Причина: на метрику ссылаются эксперименты. Если изменить её смысл («conversion» на «count»), результаты уже идущих экспериментов станут бессмысленными. Хотите другой смысл: создайте новую метрику. Это обычная практика для «неизменяемых справочников».

## 3. Метрики и guardrails внутри эксперимента

```go
type ExperimentMetric struct {          // метрика эксперимента
    ExperimentID, MetricID  uuid.UUID   // составной первичный ключ
    Role                    MetricRole  // "target" | "diagnostic"
}

type ExperimentGuardrail struct {       // предохранитель
    MetricID      uuid.UUID
    Threshold     float64
    Comparison    GuardrailComparison   // "gt" (больше порога) | "lt" (меньше)
    WindowSeconds int                   // окно наблюдения
    Action        GuardrailAction       // "pause" | "revert_to_control"
}
```

- `target`: ради этой метрики затеян эксперимент («выросла ли конверсия»).
- `diagnostic`: наблюдаем побочные эффекты (скорость загрузки).
- Guardrail читается так: «если `error_rate` за последние 10 минут больше 0.05, поставить эксперимент на паузу».

### `buildConfig` по шагам (`service/experiment_config.go`)
1. Не больше 20 метрик и 20 guardrails.
2. Для каждой метрики: роль допустимая; метрика не указана дважды.
3. Для каждого guardrail: `comparison` и `action` допустимы; окно от 60 секунд до недели; порог конечное число; один guardrail на метрику (на это же есть уникальный индекс).
4. **Один** запрос в базу за всеми метриками сразу (`GetMetricsByIDs`), затем проверка, что каждая существует и не в архиве.

Идея: сначала все дешёвые проверки без базы, потом один запрос.

### Почему при `PUT` конфигурация заменяется целиком
```go
tx.Where("experiment_id = ?", e.ID).Delete(&models.ExperimentMetric{})
tx.Where("experiment_id = ?", e.ID).Delete(&models.ExperimentGuardrail{})
// затем вставка новых
```
То же сделано с вариантами. Альтернатива («изменить только отличающиеся») сложнее и даёт больше ошибок. Для небольших списков «удалить и вставить заново» в одной транзакции проще и надёжнее.

### Как это попадает в версии (snapshot)
`json.Marshal(cur)` сериализует весь эксперимент, включая `Metrics` и `Guardrails` (у них JSON-теги). Поэтому версия 1 и версия 2 хранят разные конфигурации, и аудит работает. `ExperimentID` помечен `json:"-"`, чтобы не дублировать идентификатор внутри каждого элемента.

### Проверка перед ревью (`checkConfigForReview`)
При `submit` нужно: хотя бы одна метрика с ролью `target`, и все метрики на этот момент не в архиве. Второе важно: метрику могли архивировать **после** того, как её привязали к черновику. Отправлять на ревью эксперимент с мёртвой метрикой нельзя.

## 4. Детали базы, которые легко упустить

- Составной первичный ключ `(experiment_id, metric_id)` у `ExperimentMetric` не даёт привязать одну метрику дважды.
- Внешнего ключа на таблицу метрик нет: целостность держит сервис (проверка по каталогу). Чтобы был ключ, в модели пришлось бы объявить связь с `Metric`, и тогда GORM при `Create` эксперимента пытался бы сохранить вложенный (пустой) объект метрики. Это упрощение, его нужно записать в README.
- При `Create` эксперимента GORM сам вставляет вложенные `Variants`, `Metrics`, `Guardrails` (связь «один ко многим»). При `PUT` мы делаем это вручную, потому что нужно сначала удалить старое.
- `tx.Create(&пустойСрез)` в GORM даёт ошибку, поэтому в коде везде `if len(...) > 0`.

## 5. Права

Читать каталоги может любой авторизованный. Писать (создавать, переименовывать, архивировать) могут `admin` и `experimenter`. Реализовано через `RequireRole` при регистрации маршрутов.

## 6. Как показать проверяющему

```
POST /event-types   {"key":"exposure","name":"Показ","is_exposure":true}
POST /event-types   {"key":"purchase","name":"Покупка","requires_exposure":true}
POST /metrics       {"key":"purchase_cr","name":"CR","kind":"conversion","event_type_id":"<purchase>"}
POST /experiments   {..., "metrics":[{"metric_id":"<cr>","role":"target"}],
                          "guardrails":[{"metric_id":"<err>","threshold":0.05,"comparison":"gt",
                                         "window_seconds":600,"action":"pause"}]}
GET  /experiments/{id}/versions/1   → в snapshot видна конфигурация
```
Негативные: второй тип показа (409), метрика `count` с перцентилем (400), метрика в архиве (400), `submit` без целевой метрики (400).
